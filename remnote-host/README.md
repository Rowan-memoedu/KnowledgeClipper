# Standalone RemNote SDK host

This package belongs to KnowledgeClipper and does not import or contact the MCP service. Express serves the native API on 127.0.0.1:43111, a bounded WebSocket transport connects only the dedicated knowledge-clipper plugin on 43112, and static plugin files are served on 43113. The wire hello is knowledge-clipper.transport.v1; only bounded SDK actions are dispatched, including read-only excerpt Document discovery and verified import navigation. Disconnection/timeout never retries writes. Ping/pong clears dead peers.

Build with Build-Host.ps1 through the Windows timeout runner. Output defaults to D:\Artifacts\KnowledgeClipper\standalone-remnote\host. Deployment configuration at standalone-remnote\host-config.json requires {"pluginDirectory":"D:\\Artifacts\\KnowledgeClipper\\standalone-remnote\\plugin","mediaRoots":["<actual RemNote media directory>"]}. No MCP configuration discovery is performed. Register-Startup.ps1 registers the separate per-user task KnowledgeClipper RemNote SDK; it refuses an unowned same-name task. Registration does not start it. Start-Host.ps1 remains attached to the child process so task lifetime tracks the host; logs go to D:\AppData\KnowledgeClipper\remnote-host-logs.

The /sdk/knowledge-clipper native API requires X-KnowledgeClipper-Protocol: 1, exact loopback Host, and no Origin. Health is read-only. Export accepts a plain existing plan or {plan,newSource:true} for an explicitly known new source. Unknown source IDs must never be promoted to newSource after a failure. Readback never writes. finalize-media retains source and managed-byte SHA-256 verification and original identities.

Mermaid parts use `kind: "mermaid"` with exact source text. Health reports `mermaidSupported` for `knowledge-clipper.mermaid.v1`. `POST /sdk/knowledge-clipper/mermaid-render` accepts the frozen plan and dispatches the allowlisted `knowledge_clipper_mermaid_render_state` read. It verifies the completed content identity, then returns receipts from actual native widgets, including SVG, dimensions, labels and source hashes. Offscreen widgets may have no receipt until mounted; missing receipts never prove successful display. No diagram is converted to an image attachment.

Background operation uses the plugin's dedicated `transport-worker.js` for socket handshakes, ping responses and reconnect backoff (at most 5 seconds). The index widget retains all official SDK operations. Replies carry their original connection generation and are never resent on a replacement socket. The host owns native WebSocket ping/pong liveness; an inactive page timer must not close an otherwise healthy socket.

Navigation waits use bounded `{type:"wait",id,milliseconds}` messages on the same authenticated loopback transport. Node schedules the wakeup and returns `{type:"wait-result",id}`; at most four waits per socket and 1–1000 ms per wait are accepted, and close cancels pending waits. These messages cannot issue SDK actions or modify notes. No native window activation or RemNote launch flags are required.

`GET /health` allows a 10-second reconnect grace period and a 12-second read-only SDK probe. Its `connected`, `supported`, `sdkResponsive`, and `acceptWriteOperations` fields describe separate states. An SDK timeout must not masquerade as disabled writes or a disconnected socket. None of these waits replay an import with an unknown outcome.

`POST /sdk/knowledge-clipper/finalize-spacing` accepts only `{plan,expected,separatorRemId}` and requires `knowledge-clipper.batch-spacing-finalize.v2`. The host rereads the original content and separator, pins the complete raw node snapshot and sibling sequence, then requests the plugin's narrowly scoped same-ID completion. The plugin may finish practice settings and order only for a contiguous, journaled incomplete batch; it creates no Rems and edits no content. Edited nodes, changed identities, interleaved unrelated content, moved parents and legacy/completed journals cannot silently become a repair operation. `batchSeparatorPending` is retained as incomplete evidence, never success.

Explicit migration uses POST /sdk/knowledge-clipper/admin/adopt with {plan,expected,verifiedNodes}. An external migration procedure must first validate old live readback. The dedicated plugin then rereads original Rem/card IDs and the complete snapshot before adopting its isolated journal, creating no content. The host does not read old plugin storage or call the old service. Normal export never calls adopt.

`POST /sdk/knowledge-clipper/repair-plain-structure` requires `knowledge-clipper.plain-structure.v3` and exactly `{plan,expected,targetRemIds,expectedStructureNodes}`. The target snapshots retain missing/null/empty back distinctions and include raw direction, practice state and native card roles. The host pins all current content and structure nodes before the plugin's same-ID repair. Targets are confined to journaled directories and the original empty separator. Repair does not create, move or replace nodes; genuine back content/card roles and changed snapshots are refused. Readback remains pure. The plugin uses only official editor APIs when removing an existing empty-back delimiter and verifies restoration of the original page and selection. New multiline cards mark only answer children as card items; their top-level fronts never mark the containing directory as a card. Existing front-role readback stays compatible.

`POST /sdk/knowledge-clipper/test-plain-structure` is an explicit public fixture driver accepting `{plan,expected,separatorRemId}`. It rejects ordinary source IDs and the plugin additionally verifies the reserved public test path and marker. It only prepares an empty back on the already verified test separator and tests the same production clear function, preserving IDs and recovery evidence. No normal import, readback or repair invokes this driver.

Adoption is not an atomic transaction across journal storage and image files: the plugin pins verified original identities before the host hashes managed image bytes. HTTP success alone does not establish completed migration. The migration client must validate all returned content and hashes, then independently read back before marking completion or switching the desktop. If bytes change in that interval, retain the adopted original IDs and incomplete migration state; rerun readback/validation, never create replacements or treat the retained journal as proof of success.

Daily question plans require `knowledge-clipper.question-daily-documents.v1` (`questionDailyDocumentsSupported` in health). They pin `rootRemId` and the two configured `documentIds` to `零碎知识制卡 / question type`, append an `M.d` daily child to `documentPath`, and omit `targetDocumentId`. Only this three-level question path permits a two-ID prefix. Older fully pinned plans remain valid; the common directory writer, ordered append and separator journal are reused.

Limits retained: 2 MiB native JSON, 1000 cards, 5 document levels, 500 parts per row, 200 answer rows, 32 MiB image bytes, one image per upload request. 48 MiB WS maximum permits base64 overhead. Media path traversal/symlink escape, ambiguous media tokens, MIME mismatch and source modification are rejected.

Tests: npm test; build: npm run build. media-http.test.ts preserves the previously verified media/export regression suite with a standalone Express harness; host.test.ts covers handshake, action allowlist, duplicate session, unknown write outcomes, native HTTP boundary and explicit migration routing. Real RemNote validation remains a separate deployment check.
